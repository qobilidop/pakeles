# `tls_clienthello` — TLS ClientHello / SNI vs rustls

The TLV flagship: one Pakeles description of a TLS ClientHello whose
parse agrees, class-for-class and SNI-for-SNI, with **rustls 0.23.43**
(the public `Acceptor` API) over the committed corpus. This is the
example that forced the sized-region IR slice
(`docs/superpowers/specs/2026-07-29-sized-region-tlv-ir-design.md`):
five nested length-bounded regions (record → handshake → extensions
block → SNI extension → server_name list) and a `remaining()`-driven
TLV loop, still bounded solely by `max_depth`.

- Source: [`tls_clienthello.py`](tls_clienthello.py) (design doc:
  `docs/superpowers/specs/2026-07-29-tls-clienthello-design.md`)
- Oracle: `src/oracle/tls_clienthello.rs`; run
  `./dev.sh cargo run -- diff tls-clienthello`
- Golden factory (unprivileged):
  `./dev.sh oracle/tls_clienthello/factory/capture.sh`
  (pinned rustls via the factory `Cargo.lock`; corpus generated by
  `mk_corpus.py`)
- `gen/` holds every artifact EXCEPT a P4 parser:
  `gen/P4-UNSUPPORTED.txt` records that a P4-16 parser cannot parse
  inside a length-bounded window — the parity-plus boundary this
  example demonstrates.

## Scope

One complete ClientHello in one TLS record in one contiguous buffer —
the same assumption nginx `ssl_preread` and eBPF SNI parsers make.
Full extensions TLV walk; SNI descended to the hostname with exact
length-consistency checks at every level; all other extension types
skipped by (type, length).

**Boundaries (documented, not modeled):**

- **Cross-record fragmentation / stream semantics.** rustls buffers
  and waits (`incomplete`); a packet-pure parser sees a truncation.
  The laxness matrix maps our truncation-class reject to rustls's
  `incomplete`. A handshake length larger than its record — legal
  cross-record fragmentation — is a structural reject for us and
  `incomplete` for rustls: the one place stream semantics genuinely
  exceed single-buffer parsing.
- **rustls's post-decode policy layer** (`PeerIncompatible(*)`:
  missing signature_algorithms, etc.): fires AFTER a successful CH
  decode; projection treats it as accept-class. An extensionless
  legacy ClientHello parses cleanly on both sides — rustls then
  rejects it on policy.
- **ECH:** with Encrypted Client Hello the visible SNI is a decoy by
  design. Semantics boundary, same family as katran's config-gated
  QUIC verdict.

## Quirk catalog (found while building; ≥1-divergence rule satisfied)

1. **rustls validates the bodies of extensions it knows.** A
   zero-filled `supported_versions` body is
   `InvalidMessage(TrailingData("Empty"))` even though the outer TLV
   framing is perfectly consistent. Pakeles models unknown-type
   extensions as (type, length, skip) — a framing-exact,
   content-agnostic walk — so a body-invalid known extension is the
   real expressiveness edge between the two: agreement holds on
   framing, not on per-extension content grammars. (Corpus keeps its
   filler extensions GREASE/unknown for exactly this reason.)
2. **GREASE asymmetry is absent in rustls** (RFC 8701 works): GREASE
   cipher suites and extension types are ignored, not rejected —
   confirmed by golden entries, unlike older stacks that choked.
3. **Duplicate extensions are a parse-level reject in rustls**
   (`DuplicateExtension(0)`) — some deployed parsers (nginx preread's
   SNI scan) take the first hit instead. We model duplicate-SNI
   detection with 1 bit of parse metadata.
4. **The trailing-byte-in-record reject surfaces as a key-epoch
   error** (`PeerMisbehaved(KeyEpochWithPendingFragment)`), not a
   parse error — rustls treats the residue as the start of the next
   fragment. Structurally it IS trailing data; our record-region
   exact-pop calls it that.
5. **A record length lying past the buffer is `incomplete`, not
   malformed** — stream semantics. This forced a real refinement in
   the sized-region design: an exact-pop shortfall whose region end
   lies beyond the buffer is truncation-class, not structural
   (design doc, build-time refinements §3).

## Conformance

- `conformance/clienthello.rustls-0.23.43.golden.json` — committed,
  version-tagged rustls verdicts over `factory/corpus.txt` (31

  a truncation ladder).
