Two ways to ask a solver about a packet

Same question, different unknowns — and a ~3,700× difference in how fast z3 can answer it.

Every symex query is a question like this one, taken from a real linux_flow_dissector path:

// "Is there any packet that takes the IPIP-tunnel path?"
eth.proto = 0x0800  ∧  ihl ≥ 5  ∧  proto = 4  ∧  inner.proto = 6

Notice: the question only ever mentions fields. No constraint ever talks about "the packet" directly.

Both encodings answer exactly this question and always give the same yes/no answer. They differ only in what the unknown is while z3 is thinking.

First, why this is hard: fields move

An IPv4 header has a variable-length options region — (ihl−5)×4 bytes. Everything behind it slides. Drag ihl:

The packet, as bytes on the wire
eth14 B
ipv4 (fixed)20 B
options8 B
inner ipv420 B
tcp …
ihl = 7 → options = 8 bytes inner.proto lives at byte 51
The address of inner.proto is 14 + ihl×4 + 9 — an expression over another field. To reason about one packet byte, you first have to reason about where that byte even is. Tunnel paths chain several of these regions, so offsets become expressions over expressions.

Encoding A — the unknown is the whole packet

The original encoding gives z3 one variable: every bit of the packet, sized to the worst case (tens of thousands of bits on tunnel paths, since each var-length region is budgeted at its maximum). A field is then "the bits you find at some position of that vector."

Reading 8 bits at an unknown offset compiles to packet ≫ (w−len−off) — a barrel shifter: ~log₂(w) selection layers, each spanning all w bits. z3 bit-blasts it into a circuit of roughly w·log w gate-bits, per symbolic read — and the old code rebuilt it in a fresh solver for every one of thousands of queries, re-asserting the whole path prefix each time.
The absurdity in one sentence: to check inner.proto = 6 — a fact about 8 bits — z3 had to model a machine that can slice any 8 bits out of a 33,000-bit haystack.

Encoding B — the unknowns are the fields

The new encoding never mentions the packet. Every distinct field read becomes its own small variable — an index card, bounded to the field's width. The constraints already talk only about fields, so they translate directly.

A handful of 64-bit variables

8 bits · f₃ < 2⁸
f₀ = 0x0800  ∧  f₁ ≥ 5  ∧  f₂ = 4  ∧  f₃ = 6
// where is f₃ in the packet? — while solving, nobody needs to know

Encoding A must decide

~33,000 unknown bits
+ a shifter circuit per symbolic read

Encoding B must decide

~36 unknown bits
plain 64-bit arithmetic, zero shifters
The sliding-offset problem from the first panel doesn't get solved — it gets deleted. inner.proto is just f₃, wherever it happens to live. Query cost stops depending on packet width entirely.

Then build the packet — don't solve for it

A test vector still needs real bytes. Once z3 hands back the field values, every length is concrete — so every offset is concrete too. The packet is assembled, like inking crossword answers into the grid after solving the clues on cards:

Field values land at their now-known offsets; every unconstrained bit is zero by construction (the old encoding let z3's model completion pick junk). And a wrong assembly can't ship a wrong test: every vector still round-trips through the reference interpreter before it's accepted.

Why the answers are guaranteed identical

This works because of one structural fact about the parser IR: every read the engine can express names a region the parse cursor already placed, and the cursor only moves forward — so within a path, two different reads can never overlap. That gives a two-way bridge:

packet → fields: any packet satisfying the constraints yields field values that satisfy them — just read the regions off.
fields → packet: any satisfying field values yield a packet — the slots are disjoint, so the writes can't collide, and each value fits its slot by the width bound.

Satisfiable in one encoding ⇔ satisfiable in the other. Same feasible paths, same enumerated path set — as a theorem, not a test result. (It is also a test result: a cross-check mode, PAKELES_SYMEX_XCHECK=1, re-answers every query under encoding A and panics on any disagreement; and the path inventories are byte-identical. If a future IR feature ever lets two reads alias, the theorem breaks — that's exactly what the cross-check is left in the tree to catch.)
